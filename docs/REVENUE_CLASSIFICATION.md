# Revenue purpose reporting

Dashboard sales combine paid online order totals and store delivery values at current store prices. This is sales activity, not bank cash flow. The dashboard keeps a private cache scoped to the signed-in admin and period; refreshes run in parallel and logout clears this cache. Only the early `admin-dashboard.js` loader should fetch or paint dashboard totals.

Stats shows one income breakdown: store sales, personal orders and events, with Other/Needs review where needed. Official receipts are authoritative for amount, date and reporting overrides; matched online orders are not added again. Paid online orders without a linked receipt are added using order date and paid total (fully gift-card-funded orders do not add new income). Matching covers all dates before the selected period is filtered. A linked receipt retains online origin; the optional By source section splits online orders from other payments without changing the total. Store income here is receipts/payments, not unpaid delivery valuation. Dashboard purpose rows use the same separate category labels while retaining its operational delivery-value basis. Online receipts inherit order item/customer context and order-purpose overrides. The amount threshold never classifies an online order. Explicit coffee bars and known group customers count as events/groups; ordinary coffee products count as personal/retail. Bulk containers without clear context need review. Known stores count as retail. Non-online receipts use the provisional >₪300 group / ≤₪300 retail rule after store and group-customer matching. Recognized retail-name matches stay retail. Clear organization names (including Merkez Daf Yomi), explicit coffee-bar names, and app receipt descriptions mentioning coffee bars count as events without review. Personal or unclear names without those signals retain the provisional amount classification and stay in the review queue. Online orders still use their contents before receipt name/amount guesses. Existing manual corrections take priority. Imported receipts have only customer names and totals available; their PDF descriptions are not read by this classifier.

Corrections live in `revenue_classification_overrides`: `order-purpose:<order UUID>` changes an order and its linked receipt; `finbot:<normalized document reference>` changes only that receipt's reporting category. They never change official documents, balances, tax classifications or emails.

`finbot_income_sources` is an admin-only reporting copy of the validated private FinBot ledger, not a live FinBot read API. Use `scripts/prepare-revenue-import.py` against a new private canonical snapshot, and upsert the resulting private JSON into this table through the existing authorized import process when refreshing the export. Never add generated customer-level files to the public website. Existing FinBot accounting aggregates and their source hash remain unchanged. App-issued receipts are read live; imported and online-linked records are deduplicated by receipt reference and order identity. Payment dates are preferred where recorded; otherwise imported document dates are used.
